# 品質を検証する証拠

## 三つの証拠

1. 契約: 要件、対象ユーザー、採用DS、変更理由。
2. 実装: 使用トークン、状態管理、セマンティクス、生成物の同期。
3. 実画面: URL、ビルド、viewport、テーマ、操作前後のキャプチャと観測結果。

一つだけでは全体を保証しません。コードから見た目の良さを断定せず、スクリーンショットから操作の正しさを断定しません。

## 合否

| 観点 | 確認 | 不合格の例 |
| --- | --- | --- |
| 目的 | 初見で主要タスクを選べる | 見出しが抽象的で入口が不明 |
| 情報階層 | タイトル・本文・状態の読み順 | 全て同じカード・同じ強調 |
| 操作 | keyboard、focus、状態、回復 | 視覚的に押せるが変化がない |
| 色 | 対象ペアを数式で確認 | 装飾色でエラー文字が読めない |
| 文章 | 対象と行動と結果の一致 | 未保存なのに保存済みと表示 |
| 適応 | 320px、200%拡大、長文 | 主要操作が隠れる、横スクロール |
| 動き | reduced motion、停止、離脱 | 自動ループを止められない |
| 性能 | 初回転送、遅延読込、レイアウト安定 | 3D読込まで本文が出ない |
| ブランド | 6軸の判断と実装の一致 | 色だけを差し替えた画面 |

未検証は未検証として残します。自動計算が適合してもWCAG全体への適合宣言はしません。人の使いやすさを実証するには対象者によるタスク評価が必要です。エージェントによる仮説検証と区別します。

参考: [UI Skills improve-ui](https://www.ui-skills.com/skills/ibelick/improve-ui)。契約・実行時の観測・修正確認という考え方を取り入れ、ここでは依頼済みの修正も同じ検証サイクルに含めます。
