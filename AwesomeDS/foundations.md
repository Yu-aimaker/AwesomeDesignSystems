# AwesomeDS — Foundations

Version 1.0.0 · デザインシステムの正本

AwesomeDS は、ブランドをまだ定義していないプロダクトに適用できる、落ち着いた UI の出発点です。「すべての人・用途に唯一最適」という保証ではありません。目的、対象ユーザー、利用環境に合わない判断は、理由と検証を添えて更新します。

## 1. 判断の順序

1. 誰が、何を終える画面なのかを一文にする。
2. 主操作を一つ決め、次の操作と結果が予測できる順序で並べる。
3. 情報の優先順位を文字、余白、位置で表す。色や装飾だけに頼らない。
4. 入力前の説明、操作中の状態、失敗からの復帰を設計する。
5. 実際の幅・入力・キーボード・動きの抑制設定で確かめる。

見栄えの強いヒーロー、カードの多用、常時動く背景は必要性を説明できる場合に限定します。簡潔さは情報の削除ではなく、判断に必要な情報を適切な場所に置くことです。

## 2. 色とセマンティックトークン

正本は `AwesomeDS/tokens.json` です。スタイルは役割名から生成し、コンポーネントに独自の HEX 値を増やしません。現行 JSON は AwesomeDS 独自形式であり、DTCG 適合形式を装いません。

| 役割 | Light | 用途 |
| --- | --- | --- |
| background / surface | #ffffff | 基本の背景と主要領域 |
| muted | #f5f5f4 | サンプル領域、補助的な面 |
| text | #18181b | 見出しと本文 |
| textSecondary | #52525b | 説明、メタデータ |
| accent | #1647e8 | 主操作、リンク、選択の手掛かり |
| selection | #eaf0ff | 選択された背景 |
| border | #e4e4e7 | 装飾的な区切り |

淡い border は入力境界の唯一の手掛かりには不十分です。操作部品はラベル、形状、必要に応じて濃い境界を併用します。成功・エラーは色に加え文章やアイコンで伝えます。暗色テーマは色反転ではなく、同じ役割を保つ独立パレットです。

## 3. 文字

本文 16px、行高 1.7 を基本とし、日本語の連続した説明を無理に小さくしません。OS のサンセリフを使い、Inter / Noto Sans JP が端末にあれば使用します。フォント読込のための実行時外部通信は不要です。コードは等幅、長い行はブロック内部でスクロールします。見出しは読み順を保つ h1–h3、本文幅は目安 65–75 文字相当。意味のない英語のキャッチコピーで情報を薄めません。

## 4. 余白・形・レイアウト

余白は 4 / 8 / 12 / 16 / 24 / 32 / 48 / 64px。関連するものは近づけ、別の判断は距離で分けます。角丸は小 6 / 中 10 / 大 14px。すべてを丸いカードにせず、一覧には区切り線を使います。固定高さで文章を切り詰めません。

広い画面では左にカテゴリ、中央に内容。狭い画面ではナビゲーションを折り畳み、内容の順番は変えません。320 CSS px で主要操作と文章が横にはみ出さず、200% 拡大でも操作できます。デモとコードなど横幅が本質的な内容だけに局所スクロールを認めます。サイズのしきい値はデバイス名ではなく、内容が成立する幅から決めます。

## 5. 部品と状態

| 部品 / 状態 | 必須の振る舞い |
| --- | --- |
| Button | 動詞のラベル、主操作は領域内で一つ、連打時の重複実行を防ぐ |
| Link | 遷移に使う。操作は button。リンク先が分かる文言 |
| Input | 常設ラベル、説明、入力保持、原因と修正方法のあるエラー |
| Tabs | 選択状態を通知。タブの意味を使う場合は矢印キー操作まで実装 |
| Dialog | 名前、初期フォーカス、内部移動、Escape、終了時のフォーカス復帰 |
| Loading | 処理の意味を伝え、領域の位置が大きく動かない |
| Empty | 空の理由と次にできる操作。検索条件を解除できる |
| Error | 起きたこと、入力が残っているか、再試行・戻る操作 |
| Success | 実際に処理が成功した時だけ表示。デモはデモと明示 |
| Disabled | 理由を近くに表示。説明を hover のみに隠さない |

この表は適用先を検証する契約であり、全アプリ機能をこのサイトが実装しているという意味ではありません。

## 6. アクセシビリティ

通常文字のコントラストは 4.5:1 以上、操作に必要な非テキストの表示は原則 3:1 以上。主要操作の領域は 44×44 CSS px を設計目標にします。WCAG 2.2 AA の Target Size (Minimum) は原則 24×24 CSS px（例外あり）なので、44px を AA 必須値とは説明しません。[WCAG 2.2](https://www.w3.org/TR/WCAG22/)

キーボードのフォーカスを常に視認でき、固定ヘッダーで隠さず、スキップリンクで本文へ移動できるようにします。ネイティブ HTML を優先し、複雑なウィジェットのキー操作は [WAI-ARIA APG](https://www.w3.org/WAI/ARIA/apg/patterns/) を参照します。検証スクリプトの通過は WCAG 全項目の適合認定ではありません。

## 7. 動き

120ms は小さい反応、180ms は状態の移り変わり、280ms は領域の開閉の目安。動きは原因と結果を結び、操作可能になるのを待たせません。CSS を基本とし、3D に Three.js、ベクター再生に Lottie を必要な画面だけ追加します。ライブラリ採用は演出の目的、容量、保守性で判断し、複数のアニメーション基盤を無目的に重ねません。

`prefers-reduced-motion: reduce` では非本質的な動きを止めます。ループアニメーションには停止操作を用意し、見えていないプレビューも停止させます。動画・3D は必要になるまで初期化を遅らせ、読み込み失敗時に説明を残します。

## 8. ブランドへの展開

まず対象ユーザー、約束したい価値、競合との差、避けたい印象、利用文脈を確認します。その回答を色・書体・密度・形・動きへ対応づけます。ブランド変更でも読みやすさ、フォーカス、エラー復帰などは維持します。`DSCreator` で派生仕様を作り、変更理由、対象トークン、採用しなかった案、実画面の検証結果を残します。

## 9. 技術選定と更新

Web の既定は React + TypeScript + Vite、意味のある HTML と CSS。複雑なアクセシブル部品には shadcn/ui 等を候補とし、デモの少数の部品を理由に全ライブラリを必須化しません。モバイルでは同じ意図を各 OS の操作慣習へ翻訳します。Web の px 値を無条件に転用しません。

毎週の処理は一次情報の取得、変更検出、レビュー用レポート作成まで。内容の解釈・採否・トークン変更はレビューで行います。人気や新しさは採用理由の代わりになりません。更新時はソース、旧判断、新判断、影響範囲、検証を記録します。
